Flow walkthrough

Signup to transfer

What actually happens, in order, from the moment someone registers to the moment their first transfer lands — traced against the real Actions and Services, not a simplified retelling.

1
POST/auth/register

Register

  1. creates User — status: pending
  2. creates UserProfile
  3. looks up the cash WalletType, creates a default Wallet — balance 0.00, is_default: true
  4. creates an Otp row (purpose: registration) and returns the plain code

Gate: the account exists but is pending — login is refused until it's verified.

2
POST/auth/verify-otp

Verify OTP

  1. finds the pending Otp for this user + purpose, checks the code and the 10-minute expiry
  2. marks that Otp consumed_at
  3. updates User: status: pending → active, stamps email_verified_at

The account is now usable.

3
POST/auth/login

Login

  1. checks the password hash, then checks status === active — this is the gate Stage 1 set up
  2. creates a Sanctum PersonalAccessToken — 60 minute TTL
  3. creates a RefreshToken row — SHA-256 hash, 30 day TTL

Client now holds an access_token + refresh_token pair. Every stage below sends the access token as Authorization: Bearer ….

4
GET/wallets

First look: the wallet is already there

  1. nothing is created here — this just reads the Wallet Stage 1 already made

There's always at least one wallet to transact against before any money has moved.

5
POST/transactions

Create a transaction

Gate: a cash/bank/savings wallet can never end this step negative — only credit wallets can.

6
POST/transfers

Create a transfer

  1. locks both wallets at once, lowest id first, so two simultaneous transfers can never deadlock each other
  2. computes both new balances; guards the from side the same way Stage 5 does
  3. creates the Transfer row
  4. creates Transaction #1 — expense on the from wallet, transfer_id set
  5. creates Transaction #2 — income on the to wallet, same transfer_id
  6. updates both wallet balances
  7. fires a "Transfer Completed" Notification, then checks the from wallet for a low-balance crossing

Gate: the two Transaction rows this step creates can never be edited or deleted individually afterwards — only ever through another transfer.

7
GET/notifications

See what just happened

  1. lists the Notification rows Stages 5 and 6 created — newest first
  2. POST /notifications/{id}/read stamps read_at on one of them
  3. GET /dashboard/summary reflects the new balance immediately — it's reading the same Wallet row Stage 5/6 just updated, nothing cached

End of the journey: register → verify → login → transact → transfer → see it reflected everywhere else.

Every "creates" above is a real write in app/Services — nothing here is simplified for the diagram. Stages 5 and 6 are the only ones with branching (the balance guard); everything else is a straight sequence.
